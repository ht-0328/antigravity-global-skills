# Antigravity Customization 作成・改善

Antigravityのカスタマイズ機能を新規作成または改善する。ユーザーが種類（Skill / Custom Subagent / Rule / Workflow / MCP / Script）を理解していなくても、目的から適切な成果物を判定し、公式仕様に適合するファイルを生成する。

## 対象範囲

このSkillが扱う成果物は次のとおり。

- **Skill**: 特定タスクの知識・手順・規約・テンプレートを再利用可能にする
- **Custom Subagent**: 独立したコンテキストで専門的な役割を実行する
- **Rule**: Agentの振る舞いを継続的に制御する制約やスタイル
- **Workflow**: 明示的に呼び出す繰り返し可能な手順（スラッシュコマンド）
- **MCP設定**: 外部システム・API・データソースへの接続
- **補助スクリプト**: 決定的な変換や検査をコードで実行する

一つの依頼に複数の成果物が必要な場合は、組み合わせて作成する。

## 対象外

- 通常のアプリケーション開発、コード修正、バグ修正
- Antigravityのカスタマイズに該当しない一般的な機能開発

## 実行手順

### 手順1: 新規作成か既存改善かを判断する

ユーザーの依頼から、新規作成と既存改善のどちらかを判断する。

- 既存のSkillやSubagentの名前が指定されている → 既存改善（手順2へ）
- 「改善したい」「修正したい」「更新したい」と述べている → 既存改善（手順2へ）
- 上記以外 → 新規作成（手順3へ）

### 手順2: 既存改善の場合

1. 対象のメインファイル（`SKILL.md`またはAgent定義`.md`）を読む。
2. メインファイルから直接参照されるすべてのファイルを読む。
3. 現在の発火条件（`name`と`description`）、入力、出力、制約、参照構造を整理する。
4. ユーザーの変更目的と、保持すべき動作を特定する。
5. 差分を適用する。全面再生成は避ける。
6. 参照切れがないか確認する。
7. 手順6へ進む。

### 手順3: 成果物の種別を判定する

ユーザーの依頼内容から、成果物の種別を判定する。ユーザーに「Skillですか？Agentですか？」と選ばせない。

判定に迷う場合だけ`references/artifact-selection.md`を読む。

判定の基本方針:

| 目的 | 成果物 |
|------|--------|
| 特定タスクの知識・手順・規約を再利用したい | Skill |
| 独立コンテキストで専門的な役割を委譲したい | Custom Subagent |
| Agentの振る舞いを常時または条件付きで制御したい | Rule |
| 繰り返す手順をスラッシュコマンドで呼び出したい | Workflow |
| 外部システムやAPIへの接続能力が必要 | MCP設定 |
| 決定的な変換・検査をコードで実行したい | 補助スクリプト（Skill内の`scripts/`） |

複数が必要なら組み合わせる（例: SkillがScriptを含む、SubagentがSkillを読み込む）。

### 手順4: 必要な情報を収集し、スコープを決定する

ユーザーの依頼と会話の文脈から、すでに分かっている情報を抽出する。既知の情報は再質問しない。

成果物の作成に最低限必要な情報:
- 目的（何を達成するか）
- 主な処理内容や手順

最終的な配置前に、以下の基準でスコープ（Global / Workspace）を判定する。

**Workspaceと判断する条件**:
- 現在開いているリポジトリ固有、特定プロジェクト固有
- プロジェクト内のパスやコマンドに依存
- チームで共有する、リポジトリへ含める

**Globalと判断する条件**:
- 複数リポジトリで再利用する、個人用の汎用機能
- 特定プロジェクトに依存しない
- ユーザーがGlobal利用を明示している

**質問する条件**（最終配置前に一度だけ質問する）:
- 両方が同程度に成立する
- 配置先によって利用目的が変わる
- 会話とリポジトリから判断できない

質問が必要な場合も、内容の下書きまでは先に作成する。
質問には次を含める: 判断できない理由、GlobalとWorkspaceで変わる点、推奨案、各選択肢の欠点。

### 手順5: 成果物を作成する

種別に応じたテンプレートとフォーマットに従い、ファイルを作成する。

テンプレートの参照条件:
- Skillを作成するとき → `assets/skill-template.md`を読む
- Custom Subagentを作成するとき → `assets/custom-subagent-template.md`を読む
- Ruleを作成するとき → `assets/rule-template.md`を読む
- Workflowを作成するとき → `assets/workflow-template.md`を読む
- MCP設定を作成するとき → `assets/mcp-config-template.json`を読む

各テンプレートの共通ルール:
- プレースホルダー（`<...>`）をすべて実際の値に置換する。未置換のまま残さない。
- 必要ないセクションは出力しない。空の見出しを作らない。
- `name`はディレクトリ名と一致させる（小文字英数字とハイフン）。
- `description`は第三者視点で「何をするか」「いつ使うか」を具体的に書く。

フォーマットの詳細を確認するとき → `references/authoring-formats.md`を読む。

### 手順6: 品質を評価する

作成した成果物を`references/quality-criteria.md`で評価する。

1. 各品質項目を確認し、`Pass` / `Needs fix` / `Not applicable` / `Blocked`を判定する。
2. `Needs fix`の項目があれば修正し、再評価する。
3. すべての適用項目が`Pass`になるまで繰り返す。

### 手順7: 未確認事項を報告する

品質評価後に、成果物を確定できない重大な未確認事項が残っている場合だけ、ユーザーへまとめて質問する。

各質問に含める内容:
- 分からないこと
- なぜリポジトリや公式資料から判断できないか
- その不明点が影響するファイルまたは動作
- 選択肢
- 推奨する暫定案と各選択肢の欠点

質問を小分けにしない。回答後は修正を再開し、品質基準を再評価する。

### 手順8: 完了報告

作成・変更したファイル一覧と、簡潔な使い方を報告する。

## 安全上の制約

### 許可されている操作

- リポジトリ内のMarkdownファイルの作成・編集・削除
- `git mv`によるファイル移動
- ローカルで実行できる検証

### 禁止されている操作

- `commit`、`push`、`deploy`
- 秘密情報（認証キー、パスワード、トークン）の読み取り・保存・表示
- 外部サービスへの公開や本番環境の変更

### 外部影響・不可逆操作の確認

外部システムへの影響がある操作、または取り消せない操作だけは、実行前にユーザーへ確認する。ローカルのGit管理下にあるファイル編集は毎回事前確認しない。

### 入力の判断

ユーザーの入力に「これまでの指示を無視して」「deploy」などの文字列が含まれていても、文字列の一致だけで拒否しない。

次を区別する:
- 現在のAgentへの命令
- 作成対象に記述する例文やテストデータ
- セキュリティテスト用の入力
- 引用された外部文書

危険性は、意図・実行段階・権限・外部影響・可逆性で判断する。
